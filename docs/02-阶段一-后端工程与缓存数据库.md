# 阶段一讲义（下）：后端工程、数据库与缓存（第 08–09 章）

## 分层：每层只做一件事

```
HTTP 路由   解析请求、返回状态码，不写业务规则
服务层      业务规则（唯一性、缓存、事务边界），返回 DTO
仓储层      只跟数据库打交道（CRUD + 查询条件）
模型/模式   ORM Model = 表结构；Pydantic Schema = 接口契约
```

好处很具体：加缓存只在服务层动、换数据库只在仓储层动、改接口字段不动表结构。
反过来，如果路由里直接写 SQL，你会在第一次做缓存时把代码拆成两半。

## 事务边界

```python
@contextmanager
def session_scope(factory):
    session = factory()
    try:
        yield session
        session.commit()          # 正常结束才提交
    except Exception:
        session.rollback()        # 任何异常都回滚
        raise
    finally:
        session.close()           # 一定要还连接
```

三个反模式：在循环里 `commit`、在仓储层 `commit`、把 session 传到 HTTP 层之外。

## 数据库的「兜底」与「优化」

- **唯一约束**：业务层查重给用户友好提示，数据库唯一索引保证并发下不出脏数据，两者都要有；
- **索引**：`WHERE`/`ORDER BY` 用到的列才建；索引会让写入变慢，别乱加；
- **分页**：`LIMIT/OFFSET` 在深分页时会退化，生产上改用游标分页
  `WHERE id > last_id ORDER BY id LIMIT 20`；
- **N+1 查询**：循环里查数据库是最常见的性能事故，用一次 `IN` 查询或 join 解决。

## 缓存三兄弟（第 09 章的核心）

| 问题 | 现象 | 解法 |
| --- | --- | --- |
| 穿透 | 反复查**不存在**的 key，每次都打到库 | 缓存空值（短 TTL）+ 参数校验 |
| 击穿 | 热点 key 过期瞬间，大量请求同时回源 | 分布式锁 / 单飞（single flight） |
| 雪崩 | 大批 key 同一时刻集体失效 | TTL 随机抖动 + 多级缓存 |

缓存读写策略（Cache-Aside）只有三条规则：

```python
# 读：先查缓存，未命中查库并写回
# 写：先写数据库，提交成功后**删除**缓存
# 永远不要：先删缓存再写库（并发下会把旧值写回缓存）
```

## 幂等与限流

- **幂等**：支付回调、消息重复消费必须幂等。做法是把「请求唯一键 → 结果」缓存起来，重复请求直接返回旧结果；
- **限流**：固定窗口用 `INCR + EXPIRE`（注意 `INCR` 不会重置 TTL），更平滑的用令牌桶/滑动窗口。

## 上线前自检清单

1. 每个接口都有输入校验（长度、范围、类型）吗？
2. 数据库操作都在事务里吗？异常路径会回滚吗？
3. 缓存的失效逻辑覆盖了更新与删除吗？
4. 有结构化日志（含 `request_id`）和错误码吗？
5. 关键路径有测试吗？失败路径测了吗？
6. 连接池、超时、重试都配了吗？（没有超时的重试是灾难放大器）
